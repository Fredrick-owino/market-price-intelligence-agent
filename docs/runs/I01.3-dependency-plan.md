## Scope and result

This is a planning and compatibility review only. No package was installed,
no model was downloaded, no service was started, `.venv` was not modified, and
no application code was written. The plan targets the existing local Python
3.12.13 environment and Node 22.22.1 reported by I01.1. Proposed constraints
are intentionally broad enough for a reviewed lock; they are not claims that
the packages have been resolved together. I01.4 must resolve and test one
compatible set.

[Pydantic package metadata](https://pypi.org/project/pydantic/),

The selected MCP adapter approach is a project-owned, small adapter around the
official `mcp` v2 client/server APIs. It will normalize transport setup and
tool-result handling at one boundary. `langchain-mcp-adapters` is deliberately
not proposed: its generation and transitive compatibility with the selected
MCP v2 SDK must be proven first, and mixing SDK generations would be unsafe.

## Docker and Compose expectation

I01.1 recorded Docker Engine `29.8.2`, Compose `v5.5.1`, and daemon access
outside the sandbox. The first configuration should use a root `compose.yaml`
under the [Compose Specification](https://docs.docker.com/reference/compose-file/)
and omit the obsolete top-level `version` field. Docker/Compose is a host
runtime prerequisite, not a Python or npm dependency. The plan assumes the
daemon is available when integration checks run; it does not claim that any
container image, health check, network policy or production deployment exists.

## Compatibility decisions and unresolved conflicts

* The Python floor is 3.12, while all selected Python packages advertise a
  Python 3.10-or-newer floor. That is a compatibility signal, not proof of a
  working combined lock.
* The MCP line is explicitly v2 (`mcp>=2,<3`). A v1 adapter or a package that
  silently brings a v1 SDK must be rejected rather than mixed into the lock.
* LangGraph, `langgraph-checkpoint` and the SQLite saver must be solved as the
  official compatible family. The SQLite saver remains a local/small-project
  option and is not a release-readiness claim.
* Ollama remains a separate runtime task. No model name, weight, daemon state
  or model-performance claim belongs in this dependency plan.
* Exact `pytest-asyncio`, React DOM, TypeScript, Vite plugin and Ollama license
  metadata still require a package-metadata check during I01.4; they are
  recorded as unresolved rather than guessed.
* No `pyproject.toml`, `uv.lock`, `package.json`, npm lockfile or Compose file
  exists in this revision. I01.4 must create and review the minimum files:
  `pyproject.toml` (project metadata, Python requirement, runtime and dev
  dependency groups, Ruff/pytest configuration), `uv.lock` (generated by uv),
  `package.json` (frontend scripts and dependency groups), the npm lockfile,
  and, only if needed by the agreed runtime shape, `compose.yaml`. This task
  creates none of them.

## Safest bootstrap order and next task

1. I01.4 creates `pyproject.toml` and the frontend `package.json` with the
   proposed ranges, plus the minimum tool configuration; it does not add
   application code.
2. Run uv resolution for Python 3.12, inspect the complete dependency graph,
   and reject any MCP v1/v2 mix or incompatible LangGraph checkpoint family.
3. Generate and review `uv.lock`; separately generate and review the npm lock
   with Node 22.22.1, then run import/type/lint smoke checks offline where
   possible.
4. Only after the reviewed locks exist should the next task decide whether
   Ollama installation/runtime verification is ready. Model selection remains
   separate.

The smallest next task is therefore **creating the reviewed lock/config files
(`pyproject.toml`, `uv.lock`, `package.json` and the npm lockfile) and checking
their compatibility**. It must not install models or start services.
