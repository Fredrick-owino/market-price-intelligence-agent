## Local setup and contracts

Use the existing locked root Python environment and a local SQLite state DB.
Start a synthetic workflow with `python -m backend.app.agent.draft_recovery --db
.state/review.sqlite start --workflow-id <id> --idempotency-key create-v1`.
The legacy command is a synthetic fixture producer, not authenticated review.
For inherited borrowed MCP tests, reproduce the separately locked Fetch
environment as instructed in the I01.11 report.

Create an ignored `.env.officers.local` JSON file with an `officers` array. Each
entry must have exactly `id`, `token_sha256` (lowercase SHA-256 hex of a random
32-byte-or-longer bearer token) and a nonempty `workflows` list of permitted
workflow IDs. Keep the plaintext token in another ignored, mode-0600 local file.
Do not put it in source, frontend code, model input, logs or a URL. Keep the JSON
file restricted too. Only the **path** to it is passed in
`SOKOSIGNAL_OFFICERS_CONFIG`; `SOKOSIGNAL_STATE_DB` points to the same local DB
used by the graph. Start one loopback worker with:

```sh
uvicorn backend.app.api.review:local_app --factory --host 127.0.0.1 --port 8000 --workers 1 --no-access-log
```

Supply `Authorization: Bearer <local token>` over loopback. No endpoint accepts
identity or role in the body. The routes are:

| Route | Result |
|---|---|
| `GET /health` | Local readiness, no secret or private draft. |
| `GET /api/v1/drafts/pending` | Current pending drafts only for the officer's configured workflow IDs, including immutable content, comparison and provenance. |
| `GET /api/v1/runs/{workflow_id}/draft` | Current draft and status for a permitted workflow. |
| `POST /api/v1/runs/{workflow_id}/decisions` | Body: exact `draft_id`, positive `version`, lowercase SHA-256 `content_hash`, `decision` (`approve` or `reject`), bounded `idempotency_key` and optional `note` (at most 500 characters). Returns the stored decision and graph outcome. |
| `GET /api/v1/runs/{workflow_id}` | Current draft status, graph outcome and pending nodes; recovers a stored decision awaiting graph resumption. |

Missing/invalid bearer → 401; disallowed workflow → 403; missing draft → 404;
malformed/extra fields → 422; stale/superseded/conflicting decision or checkpoint
→ 409. The same authenticated officer's identical retry returns the original
decision. A new key cannot issue a second decision for the same version. The
SQLite transaction stores decision, draft status and audit together. Approval
sets `APPROVED` and `approved_internal_review`; rejection sets `REJECTED` and
`rejected`. Neither sends an advisory.

The graph resumes only with the stored decision validated against the current
draft and checkpoint. A crash after commit can be recovered by retrying the
decision or requesting run status. A process-local workflow lock serializes
requests in the one-worker demo; SQLite constraints serialize decision writes.

## Remaining limits

The API is local only, one worker, no external network/TLS or production identity
system. The token is static until local rotation. The verifier is an unsalted
hash, so only high entropy generated tokens are suitable. In-process locking
does not coordinate independent API workers or external CLI revisions; the store
still rejects stale writes, but cross-process graph resume needs a shared lock
or outbox. A crash during a replayable graph step relies on checkpoint and
idempotency behavior; broad fault injection and deployment backup/restore are
outside this task. Practitioner authorization and independent officer review
remain unverified. No frontend, delivery, market-data ingestion or release gate
is completed.
